# Changelog

**Release names.** `x.y.z-stage.n`: `alpha` releases bring new or untested changes for testers; `beta` releases are tested on the project's hackintosh; `n` counts the builds of one version. `z` counts fixes after a stable release, so it stays 0 until a version is declared stable, and 1.0.0 will be the first stable release. Releases up to 0.5.3 were named `-test1` (now alpha) and `-beta1`.

## 0.7.0-alpha.4

The last alpha of 0.7.0; the next 0.7.0 release is beta.1, with fixes and new defaults only. Faster Mac → iPhone transfers by default, hidden networks and enterprise Wi-Fi fixes, and the last new features of 0.7.0 behind experimental flags. **BTLEAdvFixup 0.9.8.**

**AirDrop**
- **Faster Mac → iPhone by default.** After each Block Ack from the iPhone, the next frames now go to the firmware straight away instead of at the driver's next pass (`-itlawdlcoexbarefill`, now part of the tested set). The time macOS had frames waiting while the firmware's queue was empty fell from 11.2% to 0.1% of sending time. With 105 MB files on the project's hackintosh (AX211, Tahoe 26.7.1, Wi-Fi on 36, iPhone on 149), Mac → iPhone went from about 18 MB/s to 27 MB/s on average, up to 33 MB/s. `-itlawdlnocoexbarefill` turns it off.
- **One-antenna cards** ([#97](https://github.com/retropineaple/ForbiddenItlwm/issues/97)): the rate setup for Block Ack sending to an Apple device offered two-stream rates even on a one-antenna card such as the AX101, and its firmware restarted as soon as Mac → iPhone Block Ack started (Wi-Fi dropped, sends failed). Two-stream rates are now offered only on cards that have two streams, as for the Mac's own Wi-Fi connection. Found from Lawrence629's step-by-step tests; not yet tested on an AX101. Two-antenna cards are unchanged.

**Wi-Fi**
- **Hidden networks, and three requests macOS made on every join** ([PR #107](https://github.com/retropineaple/ForbiddenItlwm/pull/107), thanks to miziho, ported from laobamac's itlwm). A hidden network is found by the name you type, and the driver remembers that name for the network's nameless beacons, so macOS can join and list it. The network's details are kept from the scan while the join is in progress, so an 802.1X join no longer ends with "Update Bss fail". On WPA2 and WPA3-Personal networks, macOS is told the link is up only after the password handshake has finished. `PM_MODE`, `WCL_FW_HOT_CHANNELS` and `POWERSAVE` are answered instead of failing, and the driver no longer waits on its command gate while Wi-Fi is going down. The review added: an access point the join asked for is never replaced by another of the same network, a hidden network only counts for the network being joined, and power save is reported off until macOS sets a level. Tested by miziho with a hidden 802.1X (EAP-PEAP) network on Sequoia 15.8.3, and here on Tahoe with an open network behind a captive portal, WPA2, WPA2/WPA3, WPA3 and a hidden WPA3 hotspot, each joining first time. It may also fix [#108](https://github.com/retropineaple/ForbiddenItlwm/issues/108).

**AirDrop with the experimental flags**
- **New `-itlawdlamsdutx`: the Mac packs two packets into one frame (A-MSDU)** when it sends to an Apple device that agreed to it. Tested here with one iPhone: hundreds of thousands of packed frames and no firmware crash. There's no clear speed change, since frames already go out in groups (A-MPDU). `ITLAWDLAmsduTx` shows what happened. An early build crashed the firmware because the packed frames were marked as padded; that's fixed.
- **`itlawdlsched=1` now covers a second 5 GHz AirDrop channel, like a real Mac** ([#45](https://github.com/retropineaple/ForbiddenItlwm/issues/45)). When macOS's plan names a second channel beside the main one (for example 44, for a nearby device that can't use 149), the listener switches there in those slots and back, sends to the devices that are there, announces the visits and answers Block Ack requests there. With only devices on 149 nearby, nothing changes. `ITLAWDLSchedSecond` shows the switches, and `-itlschednosecond` turns it off. Tested here only with a simulated second channel (`itlsimsecond`, test only), with no errors over hundreds of switches; a test with a real device on 44 is still needed.

**Bluetooth: BTLEAdvFixup 0.9.8**
- **`bluetoothd` no longer killed with "Code Signature Invalid"** ([#62](https://github.com/retropineaple/ForbiddenItlwm/issues/62), thanks to xiaoxin1262 for the crash reports). macOS can check a `bluetoothd` page again while it still holds the patches; the bytes then don't match the signature and `bluetoothd` is killed, again and again. In the reports, 15 of 20 kills were on the page with one of BTLEAdvFixup's own patches, and the rest matched BlueToolFixup's pages. Such a page now gets its original bytes for the check and its patches back afterwards. `BTLEAdvVerifyRevalidations` counts these. It only happens after long uptimes, so it hasn't been reproduced here; please report the counter after a few days.

**Diagnostics (read-only)**
- `ITLAWDLAirtime` (with `-itlawdlairtime`): where the time goes while the Mac sends to an Apple device (not on AirDrop's channel, device away, nothing to send, held back, frames waiting with the firmware's queue empty, queued), for speed reports.

**Docs**
- New [CONTRIBUTING](CONTRIBUTING.md): how to make a pull request that can be reviewed and merged.
- [INSTALL](docs/INSTALL.md): without `-btleadv`, keep IntelBTPatcher enabled, or new Bluetooth LE mice may never finish pairing ([#110](https://github.com/retropineaple/ForbiddenItlwm/issues/110)).
- [BOOT-FLAGS](docs/BOOT-FLAGS.md): the new flags.

## 0.7.0-alpha.3

Fixes for 0.7.0-alpha.2's experimental flags, two fixes found by testers, opt-in WPA3, and new diagnostics. Without the experimental flags the driver behaves as in 0.7.0-alpha.2. **BTLEAdvFixup 0.9.7.**

**macOS builds:** Tahoe 26.7.4 beta (25G422) is added, from fabio1922's `check-my-mac.pl` report in [discussion #98](https://github.com/retropineaple/ForbiddenItlwm/discussions/98): its Wi-Fi code differs from 26.7.1's, but the six IO80211 tables, the AWDL layouts the driver depends on and every import match, and BTLEAdvFixup's 26.7.3 patterns match its `bluetoothd`. The final 26.7.4 may be another build; please run `check-my-mac.pl` on it.

**Wi-Fi**
- **WPA3-Personal (SAE), opt-in with `-itlwmwpa3`** ([PR #82](https://github.com/retropineaple/ForbiddenItlwm/pull/82), thanks to ann0see; [#80](https://github.com/retropineaple/ForbiddenItlwm/issues/80)). SAE with hash-to-element (H2E) and protected management frames, ported from Eric-AirportItlwm (its SAE is OpenBSD's). Without the flag nothing changes. With it, WPA3-only and mixed WPA2/WPA3 networks join with SAE when the router offers H2E; mixed networks without H2E still join as WPA2, and WPA2 networks that offer protected management frames use them. WPA3-only routers without H2E can't be joined yet. The review added: protected management frames from the router are now received (they were dropped), only the action frames the standard protects are protected, the firmware's key flag for such stations, and a failed SAE exchange no longer cancels the next attempt. Tested by ann0see on an AX201 (26.7.3), and here on an AX211 (26.7.1): a WPA3-only hotspot joins, with Block Ack and no decryption errors, and AirDrop works both ways.
- **No more firmware crash while scanning without a connection** ([#69](https://github.com/retropineaple/ForbiddenItlwm/issues/69), found and tested by runmain). An active scan now asks for the network name on every channel, including passive and radar channels, as Linux's iwlwifi and OpenBSD do; the firmware still only listens on the channels where it may not send. Leaving the name off those channels made an AX210's firmware assert (UMAC 0x20002806) during scans while not connected: 72 times in about 55 minutes before, none in 14 hours after, in runmain's test. AX200 cards and newer; the older card families are unchanged. It can't be reproduced on the project's hackintosh.
- **Block Ack from the router before an 802.1X login finishes** ([#69](https://github.com/retropineaple/ForbiddenItlwm/issues/69)). A router's early request to aggregate is answered, as Linux does, instead of being ignored until the keys are in place; other data is still held back until then.
- **WPA3 key handling:** EAPOL key data with descriptor version 0 (used by SAE) is decrypted.

**AirDrop with the experimental flags**
- **`-itlawdlmultipeer` fixes** ([#103](https://github.com/retropineaple/ForbiddenItlwm/issues/103), [#81](https://github.com/retropineaple/ForbiddenItlwm/issues/81)), found in review after 0.7.0-alpha.2: a failed aggregated send no longer loses its first frame, and after 8 failures in a row the driver falls back to single frames; a paused, full queue no longer stops sending to every device; receive reorder state is cleared fully when a session ends and stale firmware notices for it are ignored; duplicate detection is kept per sending device; when the firmware has no room for another receive session, the request is declined and Block Ack stays on for the others; a failed send agreement is retried after 30 s.
- **Switching Wi-Fi networks with `itlawdlsched=1` no longer restarts the firmware** ([#103](https://github.com/retropineaple/ForbiddenItlwm/issues/103)). The scheduler kept its airtime request on the AirDrop listener while the driver removed the listener for the switch, and the firmware asserted; the first join to the new network then failed. The request is now cancelled first. Tested here: network switches with the scheduler on, every join first time, AirDrop both ways.
- **New experimental flag `-itlawdlamsdurx`: accept A-MSDU from Apple devices.** When an Apple device asks to pack several packets into one frame (A-MSDU) for its transfer to the Mac, the driver now agrees, as a real Mac's receiver can; the card already unpacks such frames on receive. Off by default. Tested here with one iPhone, which asked in every request: about 500,000 packed pieces received in one boot, with 6 frames rejected; no clear speed change in that small test. `ITLAWDLAmsduRx` shows what happened. The Mac still doesn't pack its own frames.

**Bluetooth: BTLEAdvFixup 0.9.7** ([#102](https://github.com/retropineaple/ForbiddenItlwm/issues/102))
- **An advertising set no longer gets another set's address.** A set with no address of its own got the last address `bluetoothd` gave any set, so the Mac could advertise twice with one address. The only fallback is now `bluetoothd`'s general random address.
- **The address goes again before a set is first switched on.** BTLEAdvFixup can't see whether the controller accepted the address it added, and `bluetoothd` can switch the set on before it arrives. A set whose address only BTLEAdvFixup sent now gets it once more, just before its first enable. `BTLEAdvEnableAddresses` counts these. Intel's own Windows driver also waits for this address to be accepted, which matches the reading. Tested here: Bluetooth and AirDrop work, no failed sends.

**Diagnostics (read-only)**
- `ITLRxBaSessions`: receive Block Ack sessions of the Wi-Fi connection and of AirDrop devices side by side (the firmware has one pool), and AirDrop requests declined for lack of room.
- `ItlwmRxErrors` ([#69](https://github.com/retropineaple/ForbiddenItlwm/issues/69)): what the Wi-Fi input errors are (decryption, replay, wrong network, too short, Block Ack window and more).
- `ItlwmWCLTrace`: the last 64 exchanges between macOS's Wi-Fi stack and the driver, for joins that fail without a trace in the driver's log.
- `ITLAWDLChainRssi`: received signal per antenna, for AirDrop frames and the router, and which antenna management frames go out on.
- `ITLAWDLPeerChannels`, `ITLAWDLSchedPlan5G` ([#45](https://github.com/retropineaple/ForbiddenItlwm/issues/45)): how many nearby devices use 44 and 149, and how often macOS plans a second 5 GHz channel. Groundwork for using both channels; the driver still uses one 5 GHz AirDrop channel at a time.
- `ITLAWDLMultiPeerGuards`: the multi-peer safety counters above.
- With `-itlfwcrashrec`, `ITLFwCrashRaw`: the newest firmware crash's error tables in full, as raw words (300 and 76 bytes, the sizes the firmware declares; the decoded fields cover the first 152 and 60), for the restarts in [#97](https://github.com/retropineaple/ForbiddenItlwm/issues/97) and [#87](https://github.com/retropineaple/ForbiddenItlwm/issues/87).

**Tested on** the project's hackintosh (Tahoe 26.7.1, AX211, one iPhone) with `-btleadv -btleadvnodupfilter itlawdlsched=3 -itlawdlmultipeer -itlwmwpa3 -itlfwcrashrec -itlawdlamsdurx`: AirDrop both ways, including after the iPhone was idle (iPhone → Mac 17–26 MB/s, Mac → iPhone about 18 MB/s after a slower first send while both devices were scanning), Wi-Fi network switches, Bluetooth, no firmware crash. Not tested here: the Sequoia and Sonoma builds (built and checked offline as before), more than one Apple device, and the #69 scan fix (this machine never hit that crash).

## 0.7.0-alpha.2

**The tested set is now the default.** Up to 0.7.0-alpha.1 AirDrop needed 18 flags in `boot-args`; from this release the driver turns them on by itself, so only BTLEAdvFixup's `-btleadv` is still needed. Old flags left in `boot-args` are still read and change nothing, and a value you set yourself (`itlawdlintcoal`, `itlawdltxqueue`) still wins. `-itlawdlnodefaults` goes back to the old rule, and `ItlwmAWDLDefaults` says which rule is in use. One flag of the set can be turned off by adding `no` after `-itlawdl` (`-itlawdlnocoexmulti`). **`-itlawdloff`** turns AirDrop off whatever else is set, so the driver works as plain Wi-Fi (`ItlwmAWDLBuildCheck` "off: -itlawdloff"). `check_compat.sh` knows the new rule, and names `-itlawdlmultipeer`, `-itlawdlpeerhandoff` and `-itlawdlstatest` among the experimental flags it finds.

The new AirDrop scheduler work stays experimental, behind the same flags as 0.7.0-alpha.1. New: one comparison flag (`-itlschedoldoverlap`) and three test-only flags.

- **`-itlawdlanybuild` makes an unverified build work like a verified one.** It now covers every build the list doesn't verify as a pair (an unknown kernel, an "expected" Sequoia kernel, or a listed kernel on an unlisted build, which before kept the announcement off even with the flag), and turns on the AirDrop packet counters as well as the announcement copy. Each keeps a runtime check: the counters now reach the peer manager through macOS's `getPeerManager()` and write only if it really is an `IO80211AWDLPeerManager`, on every build. Still at the risk of a kernel panic, for testers. Bluetooth works there when BTLEAdvFixup's patterns match the build's `bluetoothd`.
- **More macOS builds, checked offline from Apple's Kernel Debug Kits:** Tahoe 26.7 (25G229, the same Wi-Fi stack and kernel as 26.7.1) and 26.7.2's other build (25G330, identical to 25G332); Sequoia 15.8.1 (24H32, identical to 15.8), 15.8.2 (24H230 and 24H232, with 15.8.3's Wi-Fi stack and kernel), 15.7.3 (24G419), 15.7.4 (24G517) and 15.7.9 (24G830); Sonoma 14.8.3 (23J220) and 14.8.4 (23J319). Also, checked from their installers' kernel collections: Sequoia 15.7.8 (24G824, 15.7.9's kernel) and Sonoma 14.8.7 (23J520) and 14.8.8 (23J620, 14.8.9's kernel). On each, the six IO80211 tables the driver depends on are identical, the AirDrop, interface and buffer code is the same (the 15.7.x builds and 26.7 differ in NAN code only), IOSkywalkFamily's tables match and every import is present. On 15.8.1 and 15.8.2 this also turns the announcement copy back on, which has been off there since 0.6.0-beta.1. BTLEAdvFixup's Bluetooth patterns already match on 26.7, 26.7.2, 15.8.1, 15.8.2 and 14.8.8 (checked from Apple's installers).
- **BTLEAdvFixup 0.9.6: Bluetooth patterns for macOS 15.7.3, 15.7.8, 15.7.9 and 14.8.7.** The same five sites as on 15.8.3 and 14.8.9, with the same instructions around each; only call displacements differ. Each new pattern matches once in its own builds' `bluetoothd` and nowhere in the others. 15.7.4, 14.8.3 and 14.8.4 aren't checked yet (no `bluetoothd` from them).
- **The AirDrop scheduler (`itlawdlsched=1`) now runs on AX200-family cards too:** the AX200, and cards on Ice, Comet or Tiger Lake boards (AX201, AX101, 9560 class). Their firmware has the same session feature as the AX210 family's. Not tested on those cards yet.
- **With the Mac's Wi-Fi and AirDrop on the same channel** (for example a router on 149), the scheduler now makes macOS's channel-6 visits instead of staying idle. The radio is already on the shared channel for the rest. `ITLAWDLSchedSp` says "shared channel: channel 6 only". Not tested yet.
- **AirDrop stays at 80 MHz beside your router's channel, as on a real Mac** ([#26](https://github.com/retropineaple/ForbiddenItlwm/issues/26), [#101](https://github.com/retropineaple/ForbiddenItlwm/issues/101)), with `itlawdlsched=1`. Up to now two rules from before the scheduler applied: with the Mac's Wi-Fi in AirDrop's 80 MHz block on another main channel (a router on 157 at 80 MHz with AirDrop on 149, or on 36 with AirDrop on 44), AirDrop dropped to 20 MHz; with the Mac's Wi-Fi at 160 MHz over AirDrop's channel (a router on 40 at 160 MHz covers 36–64, so 44), AirDrop avoided that channel. Both came from failures when the firmware shared the radio by its own quota (#26: the iPhone never saw the Mac; PR #21: an AX201's Wi-Fi dropped during transfers). Now the scheduler asks the firmware for each AirDrop slot, so the listener keeps 80 MHz in the same block and takes its channel inside a 160 MHz one. It starts at 20 MHz, and once the scheduler has started a session it moves to 80 by the usual rules for a change (the choice holds for 60 s, with no AirDrop data for 30 s), a few minutes after joining. If the scheduler stops or the firmware restarts, the change back to 20 MHz starts without those waits; it still drains the listener's queue first, so a running transfer can be cut. Leaving a 160 MHz channel follows the normal move rules. Tested on the project's hackintosh (AX211): with Wi-Fi on 36/80 and the listener on 44/80, the listener received on its own channel and Wi-Fi kept its normal speed under load; inside 160 MHz only with a simulated 160 MHz link (the router there is 80 MHz). No AirDrop transfer has been tested in either layout yet, so please report yours. `-itlschedoldoverlap` keeps the old rules.
- **If AirDrop can't use the channel macOS picked** (country rules, for example), the scheduler pauses and AirDrop works as in 0.6.0-beta.4 until the channels match again ([#101](https://github.com/retropineaple/ForbiddenItlwm/issues/101)). Before, the scheduler then followed macOS's plan with no slots on the listener's channel, and the Mac and the iPhone never met. `ITLAWDLSchedSp` says "paused: macOS wants 44, listener on 149".
- **New opt-in flag `-itlawdlpeerhandoff`: an idle Apple device no longer blocks the next one** ([PR #50](https://github.com/retropineaple/ForbiddenItlwm/pull/50), thanks to WarnerATCN). The driver keeps Block Ack with one device at a time; when that device has gone idle and another (an iPhone, say) asks for its own session, the flag hands the session over once the idle device's queues have drained, instead of dropping the newcomer's request ([#81](https://github.com/retropineaple/ForbiddenItlwm/issues/81)). In WarnerATCN's test on an AX211 (alpha.1 base), sends to an iPhone after a native Mac failed 0/2 without it and completed 2/2 with it. Off by default; `ITLAWDLCoexPeerHandoff*` keys show it working.
- **New experimental flag `-itlawdlmultipeer`: several Apple devices can each send to the Mac with Block Ack** ([#81](https://github.com/retropineaple/ForbiddenItlwm/issues/81), [#45](https://github.com/retropineaple/ForbiddenItlwm/issues/45)). Until now the driver kept Block Ack with one device and refused the others, which then sent slowly. With the flag, each device that asks gets its own firmware station and receive sessions, the way a real Mac's firmware keeps them per device, up to one per free station the card's firmware has (at most 12; 11 on an AX211). Sending from the Mac is aggregated to each device as well: one the Mac sends a lot to gets its own aggregation queue, Block Ack agreement, sequence numbers and rate control, and its frames keep their order. Each device's own schedule, read from its sync frames, pauses its queue while it is away from the channel and holds frames sent singly until its availability window, as the driver already did for one device. A device that has exchanged nothing for about a minute gives its station back, and a failure with one device's station leaves the others alone. Off by default and untested with more than one Apple device; `ITLAWDLCoexPeers` shows each slot. The test-only flag `-itlawdlstatest` checks how many stations the firmware accepts (`ITLAWDLStationTest`). Inside, the driver now keeps each device's Block Ack state in one record.
- **`ITLAWDLSchedFollow` no longer shows `tx in session`** ([#99](https://github.com/retropineaple/ForbiddenItlwm/issues/99)). It was left over from an earlier design and always read 0. `ITLAWDLSchedSyncTx` counts the sync frames sent inside a session.
- **`ITLAWDLSchedStart` after a firmware restart** ([#101](https://github.com/retropineaple/ForbiddenItlwm/issues/101)): the restart moved its first-tick time to after the follower's start, so "follower started … after it" printed a huge number (a negative one, wrapped). The first tick is now kept for the whole boot. Display only; the scheduler wasn't affected.
- **AirDrop data frames with other per-frame values are no longer dropped.** macOS fills two bytes of every AirDrop data frame from its current settings: the minimum window extension and the presence mode. The driver accepted only macOS's default values (3 and 4) and dropped any other frame as unreadable. It now accepts any values. With `itlawdlsched=3`, `ITLAWDLRxLoss` counts the frames that carried other values ("other ext/presence"). Found by reading Apple's drivers; no iPhone has been seen sending other values yet.
- **New key `ITLAWDLListenerRxChan`** (with `itlawdlsched=1`): the listener's channel and width, and frames received by the channel the firmware reports.
- **Test-only flags** to recreate #101 without a 160 MHz router: `-itlsimsta160`, `itlsimmacchan=N` and `-itlsimunusable`. They make the driver or the firmware see something that isn't true, so never use them outside a test. `ITLAWDLSchedSp` then says "[SIMULATION]".

## 0.7.0-alpha.1

**Everything new here is experimental and behind new boot flags.** Without them the driver behaves exactly like 0.6.0-beta.4, the tested release. The AirDrop timing research of the last weeks is now part of the driver: `itlawdlsched=1` turns it on for AirDrop, and `-btleadvnodupfilter` turns on a new Bluetooth fix. Add them on top of the tested set from [BOOT-FLAGS](docs/BOOT-FLAGS.md) to try them, and say in reports that you did.

**AirDrop with `itlawdlsched=1`: how the driver now works**

Until now the AirDrop listener sat on its channel all the time, and the firmware split the radio between it and the Mac's Wi-Fi by its own rules. The Mac told other devices it was always on that channel, kept its own clock, and ignored the plan macOS makes for AirDrop. With the flag the driver works much more like a real Mac's Wi-Fi driver (HOW-IT-WORKS lists what's still different). For now it runs only on AX210-family cards (the AX210, AX211, AX411, or a CNVi card on an Alder Lake or newer board) and the Mac's Wi-Fi on another channel than AirDrop's; [BOOT-FLAGS](docs/BOOT-FLAGS.md#experimental) has the details:
- **It follows macOS's plan.** macOS's AirDrop code plans 16 slots of about 65 ms, some for AirDrop and some for the Mac's Wi-Fi. The driver asks the firmware for airtime shortly before each AirDrop slot, on a second firmware context, gives it back on time, and prepares back-to-back runs early to narrow the gap between them. `itlschedlead=N` sets how early it asks (default 12000 µs).
- **It uses the AirDrop channel macOS chose.** Before, the listener guessed the channel from what nearby devices announced. If macOS names no usable channel, the old choice is used. The channel-6 search from 0.6.0-beta.3 is off with the flag, since the driver now visits channel 6 itself (next point).
- **It covers channel 6.** Every Apple device spends one slot per cycle on channel 6. The driver now listens there in that slot, sends its sync frame there, and hands the group data it hears there (the iPhone's answers to service lookups) to macOS. It doesn't advertise that slot as AirDrop time, so no device sends it a frame there that it couldn't acknowledge.
- **It advertises the schedule it really follows,** so other devices send when the Mac is listening. While AirDrop data flows, free slots after an AirDrop slot become AirDrop time and are advertised too.
- **It keeps time like an Apple device.** It takes part in the AirDrop clock election by the rules in macOS's own Wi-Fi code, reads other devices' timing at the moment their frames were on air, and stays in step with the elected device. Its sync frames go out inside its AirDrop slots, so the timing they carry is fresh.
- **It sends macOS's announcement first.** When the Mac's AirDrop announcement changes, it goes out at once, in the slots macOS allows, ahead of other traffic. Multicast for a device goes out in that device's availability windows.
- **It gives macOS what Apple's drivers give it:** availability-window start and end events, peer cache control, AirDrop packet counters (on verified macOS builds only), and the Mac's own Wi-Fi traffic, which macOS uses to decide how much time Wi-Fi needs. It stops when macOS turns AirDrop's link off.
- **It recovers on its own.** It starts once AirDrop has been on and the listener settled for 3 s (`itlschedstartdelay=N` changes this), and resumes after the first two firmware restarts in a boot.

What this fixes on the project's hackintosh (AX211):
- **The first send after the iPhone was idle no longer fails,** even after long idle periods. The Mac's announcement used to reach the iPhone after its network announcement, so the iPhone set up the link to the Mac the slow way, and AirDrop's route check then failed.
- **Mac → iPhone no longer sits on "Waiting".** Three gaps caused it: multicast sent while the iPhone wasn't listening, a channel-6 slot advertised that the Mac couldn't serve, and the iPhone's multicast on channel 6 dropped as off-channel.

New keys under `ITLAWDLSched*`. `itlawdlsched=3` adds diagnostics for bug reports: firmware crash records (`ITLFwCrashRecords`), counts of AirDrop frames lost between the radio and macOS, and timing measurements.

Still the same with the flag: one 5 GHz AirDrop channel at a time, and Block Ack with one device at a time (#81, #45).

**Bluetooth with `-btleadvnodupfilter` (BTLEAdvFixup 0.9.5)**
- **The Mac notices the iPhone's Bluetooth changes at once.** `bluetoothd` asks the controller to report each device only once until the scan restarts. Intel controllers filter by address only, so when the iPhone changed what it advertises (for example to ask the Mac for a link), the Mac didn't see it until the next scan restart, up to about 10 s later, and sometimes not until Bluetooth was turned off and on. A Mac's own Bluetooth chip filters by content. With the flag, BTLEAdvFixup patches `bluetoothd` to scan without the duplicate filter, on every supported build.

**Tools:** `tools/check-my-mac.pl` collects what's needed to add support for a macOS build that isn't supported yet. It reads the Apple code the kexts depend on in place, and its report replaces sending in system files. It needs only the Perl that ships with macOS: no Command Line Tools, Kernel Debug Kit or installer. See [CHECK-MY-MAC](docs/CHECK-MY-MAC.md). `check_compat.sh` lists the experimental flags it finds, and `collect_hw_macos.sh` includes them in its report.

**Docs:** BOOT-FLAGS has a new Experimental section. HOW-IT-WORKS explains the scheduler. TROUBLESHOOTING, INSTALL, ROADMAP, TESTED-HARDWARE and the README are updated, and outdated "from the next release" notes are fixed.

**Tested on** the project's hackintosh (Tahoe 26.7.1, AX211, one iPhone): without the new flags, AirDrop both ways, including after the iPhone was idle, with the scheduler off as intended; with `itlawdlsched=1 -btleadvnodupfilter`, AirDrop both ways, including after idle, with every part of the scheduler running, no firmware restarts and no failed slots, and `bluetoothd` scanning with the duplicate filter off. Not tested here: the Sequoia and Sonoma builds (built, and checked offline against those macOS versions' files with `check-my-mac.pl`).

**Bluetooth**
- **Bluetooth no longer turns off after hours ([#62](https://github.com/retropineaple/ForbiddenItlwm/issues/62), BTLEAdvFixup 0.9.4, thanks to xiaoxin1262 and kodekit).** `bluetoothd` is stored compressed, and BlueToolFixup and BTLEAdvFixup patch its code in the copy of the file that macOS keeps in memory. When macOS drops one page of a 16 KB block and reads it again, APFS checks the whole block, including a page that is still patched. The check failed, `bluetoothd` crashed with SIGBUS (`KERN_MEMORY_ERROR`, "Verification failed with error 94"), and Bluetooth went off until a power-off. BlueToolFixup's patch alone is enough to cause it, so it also happened without ForbiddenItlwm. BTLEAdvFixup now keeps the original bytes of every patched `bluetoothd` page, its own and BlueToolFixup's, and gives APFS's check a copy with those bytes put back. The pages in memory keep their patches. It needs `-btleadv`, and BTLEAdvFixup loaded after BlueToolFixup, as in INSTALL. New keys `BTLEAdvVerifyHook` (1 when it's active), `BTLEAdvPatchedPages` (6 on 26.7.1), `BTLEAdvPatchedPagesFull`, `BTLEAdvVerifyRescues` (reloads that would have crashed `bluetoothd`), `BTLEAdvVerifyRescueFailures`. Checked on Tahoe. On Sequoia and Sonoma `BTLEAdvVerifyHook` shows whether it could start; if not, `bluetoothd` is patched as before.

This is the mode `itlawdlbtcoex=1` set before, now the default for everyone. `itlawdlbtcoex=N` still picks another. New key `ITLAWDLBtCoexModules` (0x15 with the multi-priority table); `ITLAWDLBtCoexMode` now reads 1.
- **BTLEAdvFixup 0.9.4 also ([PR #93](https://github.com/retropineaple/ForbiddenItlwm/pull/93), thanks to Bitboss2):** counts the Bluetooth LE commands that decide whether Instant Hotspot's connection to the iPhone can work (resolving list, address resolution, LE connections by address type). Read-only: nothing is changed or sent. New keys `BTLEAdvResolvingAdds`, `BTLEAdvResolutionOn`, `BTLEAdvResolutionOff`, `BTLEAdvResolutionEnabled`, `BTLEAdvConnectsPublic`, `BTLEAdvConnectsRandom`, `BTLEAdvConnectsIdentity`, `BTLEAdvConnectsNoResolution`.

**Wi-Fi**
- **Wi-Fi comes back after a wake ([#38](https://github.com/retropineaple/ForbiddenItlwm/issues/38), thanks to alikaylan).** On a full wake macOS could ask for Wi-Fi a few milliseconds before the card was powered back on. New key `ItlwmEnableDeferrals`. Found from a user's `-itllog` capture; not tested here (sleep is disabled on this hackintosh).

Mac → iPhone is still sent frame by frame in that setup, because the iPhone doesn't answer the Mac's request on that channel (#24). `-itlawdlnosharedba` turns it off, for comparison. `-itlawdlbaaskshared` now works there too.
- **Block-ack requests pause while AirDrop is idle.** After 30 s without data, the driver stops asking the iPhone for block ack, instead of asking for up to 10 minutes after a transfer. The next transfer starts asking again straight away. `ITLAWDLCoexBaTxIdleHolds` counts the pauses.
- **Tools:** `airdrop_measure.sh` shows the listener's width when it shares your Wi-Fi's channel. `check_compat.sh` recognises IntelBTUnified and warns that it can't be used with BTLEAdvFixup ([#32](https://github.com/retropineaple/ForbiddenItlwm/issues/32)).
- **Tested on the project's hackintosh** (Tahoe 26.7.1, AX211): Wi-Fi works, AirDrop at 17–24 MB/s iPhone → Mac and 21–26 MB/s Mac → iPhone. The Sequoia and Sonoma builds are built and checked offline, as before.
- BTLEAdvFixup is unchanged (0.9.0).

## 0.5.3-test1 (test build)

Two test flags for slow Mac → iPhone transfers (#22, #24). When the Mac's own Wi-Fi is on the same channel as the AirDrop listener (usually 149), the iPhone never accepts block ack, so frames go out one at a time. On any other channel it accepts within a second. These flags test two explanations; neither is on by default:

- **`-itlawdlbaaskshared`:** in that case, send the block-ack request without waiting for the iPhone's window. The driver's window check held back thousands of requests there. `ITLAWDLCoexBaAsksShared` counts the requests sent this way.
- **`-itlawdlhideinfra`:** leave the Mac's Wi-Fi network and channel out of AirDrop's sync frames (the infrastructure fields of the Data Path State TLV, as described by seemoo-lab/owl). The iPhone then sees a Mac that isn't on Wi-Fi. `ItlwmAWDLSyncInfraStripped` counts the frames changed.

Workaround until one of them becomes the default: put your router (or the Mac's network) on a channel other than the listener's, for example 36–48 or 157.

## 0.4.0-beta1

Everything from the 0.3.1-test1 test build (below), plus:

- **Security fixes.** A review of the driver found these, and they're fixed:
  - **Wi-Fi password handshake (WPA/WPA2):** a length check in the handshake code could be fooled by a malformed message, letting a malicious access point, or anyone who knows the network's password, corrupt kernel memory. This code comes from itlwm and OpenBSD.
  - **An old join function** copied network name and key lengths without checking them. Normal joins don't use it, but it now refuses anything that doesn't fit.
  - **The AirDrop announcement copy (`-itlawdlmitx`)** now only runs on macOS builds whose data layout was verified, so it stays off with `-itlawdlanybuild` and on unverified Sequoia versions (`ItlwmAWDLMiState` shows which). It only keeps data that looks like a real announcement. With `-itlawdlsamples`, a kernel address is no longer published in the I/O Registry.
  - **Memory and shutdown:** two memory leaks on rejected Wi-Fi frames, packets not handed back when the AirDrop interface stops, power callbacks that could run after the driver stopped, a use-after-free after a failed start, and a once-a-second health check (the watchdog) that ran without the driver's lock.
  - **One card only:** a second supported Intel Wi-Fi card is now left alone instead of corrupting the first one's state.
- **WPA2/WPA3 networks rejoin after a reboot.** Networks offering WPA2, PSK-SHA256 and WPA3 together were shown to macOS as WPA3, which the driver can't complete, so auto-join failed and macOS gave up on the whole network. They're now shown as WPA2, as with the original AirportItlwm, and the driver no longer picks PSK-SHA256 without protected management frames. Thanks to lucassaureliano (issue #9), alikaylan (issue #5) and mingww64, whose PR #1 carries the same fix.
- **BTLEAdvFixup 0.8.2:** its state is locked between threads; commands it adds time out after a second and are retried if they fail; it only acts on Intel Bluetooth controllers; and a removed advertising set no longer keeps its old random address. Its patterns also cover 26.7.2, whose `bluetoothd` matches 26.7.3's (thanks to ZEQ-Avidia, issue #8).
- **`check_compat.sh`:** no longer counts one Bluetooth pattern twice, which made it warn on 26.7.3 (issues #5, #8), and the listener check uses a more portable `grep`.
- **Removing BTLEAdvFixup before a macOS update:** an incremental update can fail while `bluetoothd` is patched (issue #8). Boot once without `-btleadv` before updating.
- **Tested** on the project's hackintosh (AX211, 26.7.1): WPA2 and open networks, AirDrop both ways, Bluetooth devices, Wi-Fi off and on, and restarts. Sleep wasn't tested.
